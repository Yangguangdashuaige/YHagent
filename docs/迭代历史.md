## 阶段 6｜增量索引 + 视频知识 + 评测体系（2026-10-15，⚠️ 本阶段代码均未提交）

### 6.1 增量索引

`cmd/indexer` 支持**增量重建**：比对"文件名 + 切片原文"复用已有向量，只对新增/改动切片调 embedding API，索引耗时与费用大幅下降；异常自动降级全量，`-full` 可强制全量。此后每次知识更新不必重建整个 4484 切片索引。

### 6.2 B 站视频知识同步 `cmd/bilisync`（10-15 晚起）

- 抓取 B 站视频（首批 **14 期《流言终结者》》**），走 wbi 签名 + SESSDATA 鉴权
- 用视频时间戳做章节锚点渲染成 md，思考模型整理（单视频超时放宽到 600s）
- 视频里"某某传言是真是假"类问题从此有据可答

### 6.3 RAG 评测体系 `cmd/eval`

- 60 条模拟真实玩家口语的评测用例（`eval/dataset.*.jsonl`）
- 指标：Hit@1/3/5/8、MRR@8，报告落盘 `eval/reports/`，query 向量带缓存
- badcase 附带命中切片标题，检索优化第一次有了客观靶子

## 阶段 8｜联网搜索 + 确认入库闭环 + 工程化（2026-10-17，⚠️ 未提交）

让 AI 在知识库没有资料时**联网搜索**，搜索结果经玩家确认、管理员审核后**沉淀进知识库**，下次直接本地命中。

**后端**

- `internal/websearch`：火山方舟 Responses API 原生联网（`web_search` 工具）；真实响应解析（搜索词、`url_citation` 来源精确提取、logo 图片链接过滤、URL 去重），含 15KB 真实响应样本单测
- `knowledge/ExtraStore`：运行时**补充知识库**（主索引 embed 只读，补充层双指针归并检索、原子落盘、重启自动加载、坏索引备份）
- `internal/ingest`：AI 把联网摘要整理成规范攻略 md（禁止脑补、强制标题/分节/来源落款）→ 切片 → 每批 16 条向量化 → 入库
- `POST /v1/knowledge/ingest`：`X-Admin-Token` 恒定时间比较鉴权（未配置 503 / 错口令 403）、240s 超时
- SSE 新增 `candidate` 事件推送联网候选卡片；system prompt 新增"游戏语境优先、知识库不足先联网、末尾列来源、不得谎称已收录"规则；工具超时 25s → 45s

**前端（网页版）**

- 回答下方出现黄色「🔎 联网知识 · 待确认入库」卡片（搜索词、来源链接、采纳/仅参考）
- 内联管理员口令输入（替代 window.prompt，兼容手机 webview），成功后卡片变绿
- **10-17 晚优化**：入库接口改 SSE，口令对错**即时反馈**（错→红字"管理员口令错误，请重新输入"且不缓存；对→校验项秒变绿勾）；**入库进度面板**四步步骤条（校验→AI 整理→切片向量化→写入）+ 计时器 + 向量化 x/N 百分比 + AI 撰写逐字实时预览 + 心跳保活 + 失败重试

## 阶段 9｜评测集重写 + BM25/RRF 混合检索 + 仓库治理（2026-10-18）

### 9.1 评测集全量重写（R001-R100）

- 旧 E001-E110 全部废弃，自底向上重写：每条 expected 均与真实 `index.gob` 切片条目逐一核对
- 三类分布：物品 41 / 公告 29 / 机制 30；自定义 qtype 体系：lookup / attr_lookup / paraphrase / compare / date_lookup / entity_agg / confusable / colloquial / multi_hop / robust
- 难例代表：跨年同日期公告（R053 4月16/17 双赛季）、多跳"干员代号→赛季"（R045/R046）、地图+主题钥匙聚合（R037 旅馆钥匙）
- **纯向量新基线**：切片级 Hit@1 84.0% / Hit@8 99.0% / MRR 0.903；文件级 89.0% / 100% / 0.938；薄弱 qtype：entity_agg 50%、multi_hop 50%

### 9.2 BM25 + RRF 自适应混合检索

- 新增 `internal/knowledge/bm25.go`（零三方依赖）：自定义分词器——汉字二元组 + ASCII 整词（`7.62x51mm`/`K416`/`DVC12+P` 不拆散）；**词元字符必须 ASCII-only**（`unicode.IsLetter` 匹配汉字，会把"8月14日的…"吞成单巨型词元导致检索落空）；进程内倒排索引；标题（面包屑）3 倍权重；k1=1.2、b=0.75
- `store.go` 新增 `SearchHybrid`：向量 + BM25 双通道各取 Top-50，RRF（k=60）加权融合；**BM25 权重自适应**——查询含数字（日期/编号/规格）等权 1.0，纯中文语义查询降权 0.15（等权融合实测反而使 Hit@1 降到 80%，BM25 噪声压过向量正确 Top1）
- 纯向量 `Search` 零改动（回归校验与基线逐字节一致）；`cmd/eval` 新增 `-mode=vector|bm25|hybrid` 三模式
- **成果**：切片级 Hit@1 84→88、Hit@8 99→100、MRR 0.903→0.923；文件级 89→95、零 badcase；R053 rank 35→4；date_lookup 20%→80%、multi_hop 50%→100%
- 生产入口切换见 9.4（`search_knowledge` 已全链路走混合检索）

### 9.3 仓库治理

- 阶段 5～8 全部积压代码分 6 个提交入库（`bd4ff78`…`bbfd527`）
- 知识库 1967 个 md 源文件整体迁至 `server/data/knowledge/` 并退出 git 跟踪（`.gitignore` 增加 `server/data/`），git 面板不再被未跟踪文件刷屏；知识内容仍以 `index.gob` 形式版本化
- 四个工具默认路径同步指向 `data/knowledge`（indexer `-src`、crawler / itemsync / bilisync `-out`），用法不变（仍在 `server/` 下运行）

### 9.4 生产检索切换混合（search_knowledge 全链路）

- `Searcher` 接口扩展 `SearchHybrid`（query 向量 + 原始文本双入参），`*Store` / `*ExtraStore` 双实现
- `ExtraStore.SearchHybrid`：向量通道 = 主/补两侧余弦归并 Top-50（余弦分跨库可比）；BM25 通道 = 两侧关键词子榜单按原始分归并后截 Top-50（两侧语料规模悬殊、IDF 不严格可比，由 RRF 名次制强阻尼，不做索引合并）；补充库整体替换式重建，BM25 索引随 `*Store` 实例惰性构建、随旧实例回收，**无需失效逻辑**
- 融合核心抽公共 `fuseRRF`（按 Chunk.ID 归并通道名次，主索引全局连续编号、补充索引接续编号保证键唯一）；权重门控抽 `bm25WeightFor`；重构后评测回归与 9.2 逐指标一致（Hit@1 88.0% / Hit@8 100% / MRR 0.923）
- tool.go 切换调用 `SearchHybrid`；「相关度」由余弦分改为相对第一名的归一化名次分（RRF 原始分 ~0.01-0.03，直接展示易被模型误读为弱相关）
- 新增 `extra_store_test.go`：补充切片经 AddDocument 入库后可被混合召回、空补充库退化为主索引检索、结果确定性、接口编译期断言

### 9.5 标题末段加重进向量（修复 R098，全量重嵌）

- 根因：R098「赤枭巡猎能选什么难度和行动」的答案切片标题恰是「可选择行动及难度」——意图词（难度/行动）只存在于**标题**，占 600 字开头十几个字，在稠密向量里被正文稀释；BM25 词频哲学修不了（下架提醒等"赤枭巡猎"词频最密的 chunk 理直气壮排前面）
- 第一版 `title2x`（整条面包屑加权）**实测翻车**：面包屑大头是文档名前缀，整条加权让同文档所有小节互相拉近，顶层摘要片（标题=纯文档名）失去区分度——Hit@1 88→86，已修好的 R053 又坏了
- 终版 `titleleaf2x`（`EmbedInput` = 面包屑**最深小节名**单独一行 + Content）：只加重每个切片独有的内容标识；摘要片末段=文档名（含日期），日期查询区分度反而提高。`Store` 新增 `EmbedVer` 输入格式版本字段，indexer 加载时校验版本不符自动全量重嵌（避免旧格式向量被增量复用的静默错配）
- 4484 片全量重嵌后（query 向量缓存不受影响）：**fine 口径 Hit@1 89.0%（+1）/ Hit@5 99.0% / Hit@8 100% / MRR 0.929（+0.006）**；R098 rank 7→4 修复、R053 4→1、confusable 与 colloquial 双双 100%；coarse 口径 93.0%/MRR 0.960。代价：5 条物品 lookup 从 rank1 滑到 2/3（近名物品干扰，Hit@3 内），纯向量新基线 85.0%
- 剩余边界 badcase：R042（日期查询 rank 6，Hit@8 内）、R035（coarse 近名干扰 rank 5）——继续调参边际收益递减且有针对 100 条评测集过拟合风险，标记为已知边界

### 9.6 检索结果重排 rerank（LLM 路线已上生产）

- **动机**：Hit@8 已 100%，剩余错误全是排序问题（近名物品 rank 2-3、R042 日期 rank 6）——正是 rerank/cross-encoder 的精确适用场景
- **调研纠偏**：方舟 `/api/v3/rerank` 实测不存在（空体 404，对照坏模型名在已知端点会返回带 JSON 的 404），官方模型列表亦无 rerank 模型；火山 rerank 模型统一挂在 **VikingDB 服务**下（`doubao-seed-rerank`，HMAC-SHA256 V4 签名 + IAM AK/SK 鉴权）。故 Reranker 抽象出两个实现同台对比
- `internal/ai/rerank.go`（零三方依赖）：
  - `Reranker` 接口 + `RerankDoc`（标题+正文）；`SortDocsByScore` 稳定降序
  - **LLMReranker**：复用 ARK key 走 chat 接口，`thinking:disabled` + temperature 0.1 列表排序；输出解析三级鲁棒（JSON→围栏剥离→全文数字扫描，越界/重复剔除、缺号按原序补尾，恒返回合法全排列）；位置换算单调分数，超 50 候选截断垫底
  - **VikingReranker**：`/api/knowledge/service/rerank` 直调（datas≤200，返回逐条分数）；V4 签名与 volc-sdk-golang `base.Sign4` 逐字段对齐（含 `X-Content-Sha256` 头签名——初版漏了它，对照 SDK 源码补上）；`rerank_instruction` 对齐控制台默认指令
- 配置全显式开关（留空=不启用，防未开通模型刷无效调用）：`ARK_RERANK_LLM_MODEL`（LLM 路线）/ `VOLC_ACCESSKEY`+`VOLC_SECRETKEY`（Viking 路线，host 与模型有官方默认值）；生产构造顺序 **Viking 优先、LLM 兜底**
- eval 新增 `-rerank=none|llm|viking` + `-rdepth`（重排候选深度，默认 30）：检索先取深度候选 → 重排 → 截断到 k；单条失败保留原序并计数，报告落盘含重排器名/深度/失败数

## 阶段 11｜可观测性 trace 层：请求级全链路调用观测（2026-10-19）

**动机**：此前整个系统只有 `log.Printf` 散点日志——"这题为什么答了 8 秒""豆包这轮烧了多少 token""缓存到底命中没有"全靠人肉翻日志拼线索。补一个最小的 trace 层，让每次 `/v1/chat` 的执行过程变成一条可查的结构化记录。

### 11.1 数据与落盘（internal/trace，零三方依赖）

- **一条 trace = JSONL 一行**（`data/trace/trace-YYYYMMDD.jsonl`，按天轮转、保留 7 天可配 `TRACE_KEEP_DAYS`、每小时+跨天自动清理过期文件）：trace_id / 会话 / 提问 / LLM 轮数 / **每轮耗时与 token 用量** / **每个工具的耗时、入参摘要、结果字节数、成败** / 三角洲缓存命中与未命中次数 / 总延迟 / 首 token 延迟（TTFT）/ 回答字数 / 失败原因
- **Span 全链路 nil 安全**：`Recorder` 未启用（目录创建失败/未配置）时 `Start` 返回 nil，埋点全 no-op，业务零感知、零判空样板代码；埋点经 `context` 传播（`WithSpan`/`FromContext`），函数签名零侵入
- **Recorder 写路径**：`sync.Mutex` + 跨天自动切文件 + `json.Marshal` 后追加单行写；读路径 `Recent(n)` 多文件倒序、单文件 Scanner 尾读（8MB 上限防异常大文件），非法行跳过
- preview 工具入参/提问摘要：压缩空白 + 字节截断且对齐 UTF-8 合法边界（截断点落在汉字中间会产出非法 JSON 字符串）

### 11.2 埋点接入（改动最小的原则）

- **token 用量**（[client.go](../../server/internal/ai/client.go)）：请求开 `StreamOptions.IncludeUsage`，豆包流式响应在**末 chunk**（choices 为空）携带 usage；新增 `onUsage` 回调注入 Agent。为此 `FinishReasonToolCalls` 分支从"立即返回"改为"标记后继续读到 EOF 再交付工具调用"——否则提前退出会丢掉末 chunk 的统计；finish 之后的流异常不视为失败（工具调用已完整收到，保持原语义）
- **Agent 循环**（agent.go）：请求入口 `Start` + defer `End`（错误信息也入 trace）；每轮 LLM 计时 + usage 落 Span；首个文本 chunk 记 TTFT；`executeToolSafe` 增加 round 参数，panic 恢复/超时/截断降级均记为工具失败
- **缓存命中**（deltaapi/client.go）：`doGet` 收敛为单次记账——从缓存拿到（含 singleflight 临界区二次命中）记 hit，真正请求上游记 miss；领头者等 singleflight 合并期间别人填充了缓存，最终也会记成 hit，不会 miss+hit 双计
- **查看接口**：`GET /v1/traces?limit=N`（默认 50、上限 200）双鉴权——访问码（`withAuth`）+ `X-Admin-Token` 恒定时间比较（trace 含各会话提问内容，不开放给普通访问码用户）；`Tracer` 未配置返回 503，与知识入库接口同款行为

### 11.3 网页观测页 /trace.html

- 自包含单文件（零依赖，与聊天页同款暗色主题），`go:embed` 的 FileServerFS 自动暴露路由
- 顶部汇总卡：样本数、成功率、平均耗时、平均首字、LLM token 总量、三角洲缓存命中率；下方 trace 列表可展开看 LLM 轮次表（轮/耗时/输入/输出/合计 tokens）与工具调用表（轮/工具/耗时/结果字节/缓存/状态/入参摘要）
- 访问码复用主页 `yh_token`，管理员口令复用入库流程的 `yh_admin_token`（验证通过才缓存，错误即清除）；`autocomplete="new-password"` 防浏览器密码管理器误填

### 11.4 真实冒烟（本地起服务，三条典型链路）

- **纯对话**：1 轮 LLM，prompt 4881 tokens（26 个工具定义的固定开销从此可量化）、TTFT 787ms、总 2.3s，落盘 JSONL 可查
- **工具调用**（"今天的地图密码是什么"）：2 轮 LLM + `delta_map_password` 141ms/2003B 未命中 + `delta_map_today` 469ms 命中，重排后工具轮 2394 prompt tokens——多跳链路完整还原
- **缓存复用**（同问题再问）：同工具 0ms + `cache_hits:1`，与首问的 141ms/miss 形成对照
- 单测：trace 包 5 个用例（nil 安全、读写回路、非法行跳过、过期清理、UTF-8 边界）+ server 包 `/v1/traces` 双鉴权与 503 行为

## 阶段 12｜响应体感优化：工具进度可视化 + 同轮并行执行（2026-10-19）

**动机**：联网场景回答要 15-60s，但发送后只有三个点在跳——工具执行全程静默，玩家不知道是在搜索还是卡死了；且同轮多个工具（密码+价格双查询）是串行执行的，白等。trace 数据显示单次请求里 LLM 各轮 3-30s、web_search 5-14s，全程可见进度能把"卡住感"变成"在干活"。

### 12.1 SSE `tool` 事件：工具执行进度实时推送

- **协议**：新增 `event: tool`，`{"name":"web_search","phase":"start","label":"联网搜索"}` → `{"name":"web_search","phase":"end","ms":13965,"ok":true}`；与 candidate 事件同款实现模式——`ai.WithToolEventFunc` 经 context 注入回调（[toolevent.go](../../server/internal/ai/toolevent.go)），`executeToolSafe` 执行前后发射，函数签名零侵入；旧客户端（Wails 瘦客户端）对未知事件自然忽略，协议向后兼容
- **服务端标签映射**（server.go `toolLabel`）：web_search→联网搜索、search_knowledge→知识库检索、delta_*→游戏数据查询、gun_build→改枪方案生成等

### 12.2 网页端实时状态条

- 回答气泡结构改为「状态条 + 独立正文 span」：流式重绘只更新正文 span，状态条不被冲掉（此前 innerHTML 整体重绘会把子元素抹掉，这也是候选卡片只能事后插入的原因）
- 三态：`🧠 思考中…`（首个 LLM 轮 TTFT 期间）→ 每个工具一枚 chip（旋转图标 + 实时 0.1s 精度计时）→ 完成变 `✓ 联网搜索 14.0s`（失败红色 ✗）；多工具并行时各自独立计时并列展示
- 请求结束才移除状态条（保留各工具耗时供玩家回看）；断连/异常时清理全部计时器防泄漏

### 12.3 同轮多工具并行执行

- **Agent 工具循环并行化**（agent.go）：同轮 `pendingCalls` 用 WaitGroup 并行执行（各自独立超时/panic 恢复不变），全部完成后**按调用顺序**落 tool 消息——tool 消息顺序必须与 tool_calls 一致，所以先并行收结果、再按序 append 会话历史
- **并发安全加固**（并行化的连带必要改动）：① trace `Span` 全部记录方法加互斥锁（并行工具同时 `ToolCall`/`NoteCacheHit`）；② SSE 写入统一 `writeMu` 串行化——并行工具的 candidate/tool 回调来自不同 goroutine，心跳协程也在写，不加锁会响应撕裂（旧代码理论就有此竞争，碰撞概率低未暴露）
- **系统提示词第 9 条**：引导模型"多个互不依赖的工具在同一轮一起发起"（模型本就支持同轮多 tool_calls，此前串行执行浪费了这一能力；实测第 1 轮即并行发出密码+物品双查询）
- 收益：同轮工具耗时从累加变取最大值；配合引导省掉"查完知识库再决定联网"的整轮 LLM 调用（2-4s）

### 12.4 冒烟验证（真实链路）

- 多工具问题（密码+曼德尔砖价格）：trace 显示 round1 两工具（128ms/144ms 并行）、round2 两工具（57ms/70ms），并行记录零竞争
- 联网问题：`delta_map_password`(0ms 缓存命中) → `search_knowledge`(423ms) → `web_search`(13965ms)，全程 12 个 tool 事件按 phase 配对推送，前端状态条实时可见
